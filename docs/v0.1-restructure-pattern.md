# v0.1 Restructure Pattern — fullstack entry consolidation

Written for the `v0.1-restructure-fullstack` phase. Records the pattern
chosen and the alternatives weighed. See `PORT-FULLSTACK-1` in
`docs/CONVENTIONS.md` for the codified rule.

## Problem

`dx serve --platform web --package server` failed with a `mio` wasm-compile
error because `dx` tried to build the `server` crate (which uses
tokio + axum + reqwest) for the `wasm32-unknown-unknown` target.

Root cause: Dioxus 0.7 Fullstack expects **one crate** that compiles twice —
once for the native (server) target and once for the WASM (web) target.
Splitting server host code into a separate `server` crate and UI code into
`ui` means `dx` has no supported way to express "build the server side from
crate A and the web side from crate B."

## Patterns evaluated

### Pattern A — `dioxus::serve` with `dioxus::server::router`

```rust
fn main() {
    #[cfg(feature = "server")]
    dioxus::serve(|| async move {
        let router = dioxus::server::router(App)
            .route("/api/contact", post(contact))
            .route("/api/pageview", post(pageview))
            .nest_service("/assets", ServeDir::new("assets"));
        Ok(router)
    });

    #[cfg(not(feature = "server"))]
    dioxus::launch(App);
}
```

Official Dioxus 0.7 docs pattern. Uses `dioxus::serve` to inject custom routes
into the default Dioxus Axum router. Requires our own `reqwest` dep for Mailgun.

**Rejected:** dioxus::serve + dioxus::server::router is new API surface not
yet exercised in this codebase; switching would require full re-verification of
handler behavior. Per PORT-ROBUST-1 (robustness > terseness) the working
existing handler chain is preferred.

### Pattern B (first attempt) — feature-gated entry points

```toml
[features]
default = []
server = ["dioxus/server", "dep:axum", "dep:tokio", ...]
web = ["dioxus/web"]
```

```rust
#[cfg(feature = "server")]
#[tokio::main]
async fn main() -> anyhow::Result<()> { ... axum::serve ... }

#[cfg(not(feature = "server"))]
fn main() { dioxus::launch(App); }
```

Ran `dx serve @server --features server @client --features web`.

**Rejected:** `dx` leaks `--features server` into the WASM build (build output
path: `target/wasm32-unknown-unknown/server-dev/`), causing `mio` compile errors.
`@client --features web` adds features to the client build ADDITIVELY rather than
exclusively overriding them. Feature-based gating is insufficient when `dx`
controls both compilation invocations.

### Pattern C — target-based gating (CHOSEN)

```toml
[dependencies]
dioxus = { workspace = true }           # fullstack + router (all targets)
thiserror = { workspace = true }        # compiles for wasm32 harmlessly
serde = { workspace = true }
serde_json = { workspace = true }

[target.'cfg(not(target_arch = "wasm32"))'.dependencies]
dioxus = { workspace = true, features = ["server"] }  # merged: adds server feature native-only
axum = { workspace = true }
tokio = { workspace = true }
tower = { workspace = true }
tower-http = { workspace = true }
reqwest = { workspace = true }
tracing = { workspace = true }
tracing-subscriber = { workspace = true }
anyhow = { workspace = true }
```

```rust
#[cfg(not(target_arch = "wasm32"))]
#[tokio::main]
async fn main() -> anyhow::Result<()> { ... axum::serve ... }

#[cfg(target_arch = "wasm32")]
fn main() { dioxus::launch(ui::App); }
```

Cargo automatically excludes the `[target.cfg]` deps when building for
`wasm32-unknown-unknown`. `dx serve --platform web --package ui` works with NO
`@server`/`@client` feature flags — each target gets the right deps via Cargo's
own platform resolution.

The `dioxus = { features = ["server"] }` entry in the target-specific section is
merged with the base `dioxus` dep on native, giving `["fullstack", "router",
"server"]`. On wasm32, only `["fullstack", "router"]` apply — `dioxus/server`
(which pulls in a tokio/mio chain) is excluded.

**Why Pattern C:** PORT-ROBUST-1 (robustness > terseness). Feature-based
gating has a hidden coupling to `dx`'s feature-pass behavior; target-based
gating is immune — Cargo's platform resolution is authoritative and predictable
regardless of which tool invokes the build.

## Build commands after restructure

```bash
# Native server (all server deps auto-included)
cargo run

# WASM check (server deps auto-excluded)
cargo check -p ui --target wasm32-unknown-unknown

# Integration tests (native — all deps available)
cargo test --workspace

# Fullstack dev server (no flags needed — target cfg handles dep splits)
dx serve --platform web --package ui
```

## Key insight: Cargo merging duplicate dep entries

When the same package appears in both `[dependencies]` and
`[target.cfg.dependencies]`, Cargo **merges** their feature sets. This is the
mechanism used to activate `dioxus/server` only on non-wasm32 targets without
a separate feature flag or duplicate dep specification.
